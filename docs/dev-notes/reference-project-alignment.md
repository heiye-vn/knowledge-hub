# 与参考项目的对照策略

> **为什么单独记这份**
>
> `knowledge-hub` 会**持续参照** `knowledge-hub-backend`（只读，分支 `v3`）进行开发，
> 后续每做一个模块都要先问：「参考项目这块是怎么做的？」
>
> 但「照做」和「照抄」是两回事。这份笔记记录的是**讨论过程中形成的判断标准**——
> 什么该照搬、什么可以换、什么必须改。
>
> **分工**：本文件讲**判断方法**；具体的模块映射与分叉登记见
> [reference-mapping.md](../reference-mapping.md)，不要在这里重复罗列。

---

## 1. 三层判断法（核心）

参考项目的价值按三层划分，判断落在哪一层，就决定了该怎么做：

| 层 | 含义 | 做法 | 典型例子 |
|:---|:---|:---|:---|
| **模式层** | 与技术选型无关的**结构、职责切分、契约形状、幂等模式** | **照搬** | 管线形状「清旧块→分块→嵌入→写库」；chunkId 生成规则；模块命名 |
| **实现层** | 具体用的**中间件、库、协议** | **可换**，换完登记一行 | 队列 RabbitMQ→BullMQ；检索入口路径 |
| **缺陷层** | 参考项目**踩过的坑** | **必须改**，且要写清怎么改 | 装了 IK 未指定 analyzer；软删除不清向量；只写不读 |

**判断口诀**：换掉一个东西后，如果参考项目里已有的知识和经验**依然适用**，那就是实现层，随便换；
如果换掉后参考项目就**不再能作为对照**，那要慎重。

### 实例：为什么检索入口不用 `/documents/search`

spec 里原本写 `POST /documents/search`（参考项目风格），
实际实现成 `/search`（GET + POST）。这是**实现层**分叉——
路径变了不影响管线逻辑的可对照性，反而语义更清晰。已登记。

### 实例：为什么服务命名必须沿用

`ChunkingService` / `EmbeddingService` / `VectorIndexService` / `RagOrchestrator`
**刻意同名**。这看似小事，实际是**模式层**决策：
后续想查"参考项目这块怎么实现的"时，能直接 grep 同名文件对照。
**不要为了命名风格去改名。**

## 2. 已形成的决策共识

按「当时为什么这么定」记录，避免日后只看到结论、看不到前提。

| 决策 | 结论 | 当时的权衡 |
|:---|:---|:---|
| 向量库 | **与参考项目一致用 ES**（曾评估 pgvector） | 中文 BM25 是硬需求；PG 侧需 `zhparser`（编译、绑版本）成本高。代价是失去同库事务，用「清理 + 检索侧兜底」补偿 |
| 队列 | 阶段一**同步**；阶段二 BullMQ（非 RabbitMQ） | Redis 本就在规划内，零新增组件；BullMQ 自带重试/退避/任务状态，直接根治参考项目的消息丢弃缺陷 |
| 中文分词 | **显式指定** `ik_max_word` / `ik_smart` | 修参考项目 P1：不指定则走 standard 切成单字，IK 白装 |
| Embedding 初始化 | **延迟初始化** | 修参考项目 P1：构造期 throw 会拖垮整个应用启动 |
| 检索能力 | **补上**（参考项目完全没有） | 参考项目只有写入没有读取，管线是单向管道 |
| 删除联动 | **清向量 + 检索侧兜底** | 修参考项目 P0：软删除不清向量，已删文档仍能被召回 |

> 每条改动若属"缺陷层"，务必在代码注释里写清**修的是参考项目的什么问题**，
> 否则后来者会以为是过度设计而简化掉。

## 3. 后续开发的对照流程

做新模块时建议按这个顺序走一遍：

1. **先找参考项目对应模块**（`knowledge-hub-backend/src/` 下 grep 同名或近义词）。
2. **判断属于哪一层**（模式 / 实现 / 缺陷），按第 1 节的表决定照搬还是替换。
3. **翻一遍参考项目该模块的已知缺陷**
   → [reference-mapping.md §四](../reference-mapping.md) 有清单，先看有没有命中。
4. **实现时保持可对照性**：模块/服务命名尽量同名，注释里可写「与参考项目 X 一致 / 差异在于 Y」。
5. **登记**：有分叉就到 `reference-mapping.md` 分叉表加一行（日期 + 分叉点 + 理由）。
6. **收尾**：在 `docs/dev-notes/` 新增该模块的过程记录（见 [README](./README.md)）。

## 3.5 收尾时的验证闭环（易错）

`pnpm build:server`（`nest build`）用的是 `tsconfig.build.json`，其中有
`"exclude": ["**/*spec.ts"]`。**这意味着测试文件的类型错误不会被构建发现。**

2026-09-19 实际踩到：写完 `document.service.spec.ts` / `vector-index.service.spec.ts` 后
跑 `build` 全绿，但 `tsc --noEmit -p tsconfig.json`（含 spec）报 4 个错——
两处是 fake 依赖的签名收窄、两处是 ES `SearchHitsMetadata.total` 可选属性导致的签名不兼容。

**因此收尾必须跑三条，缺一不可：**

```bash
pnpm typecheck:server   # tsc --noEmit -p tsconfig.json（含 spec）
pnpm test:server        # vitest
pnpm --filter @knowledge-hub/server lint   # oxlint，只看 error
```

已把 `typecheck` 固化成脚本（`apps/server/package.json` + 根 `typecheck:server`），
不要再用 `build` 代替类型检查。

## 4. 需要留意的倾向

讨论过程中出现过、后续要避免的两种偏差：

- **不敢改**：明知参考项目有缺陷，却因为"保持一致"照抄。
  → 缺陷层就是要改，改完写清理由即可。
- **改得没痕迹**：换了实现却没登记，时间一长就分不清是"有意分叉"还是"无意漂移"。
  → 分叉登记表就是为这个存在的，花 30 秒加一行。
